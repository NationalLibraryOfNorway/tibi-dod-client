# Content is issued explicitly, and every path, host and size the Service names is untrusted

`dod download` never calls `issueContent` itself: issuing is a separate, explicit `dod issue`, because the loan state it changes is exactly what a test client must be able to observe. Downloading content that was not issued must reach the Service so that its `invalidParameter` fault from `getContentResources` is reported as it came; an implicit issue would hide that behaviour and make "reading a book you have not borrowed" untestable.

Everything a `resources` answer names is treated as untrusted input. All `localURI` values are validated before the first byte is fetched (relative, no `..`, no backslashes or drive letters, still inside the target directory after normalisation), and one bad entry aborts the download with nothing written. Files are written to a `.part` file and renamed only when the byte count matches `size`; existing files are never overwritten without `--force`. Resource URIs on another host than the Service are refused unless the user passes `--trust-host` (ADR 0002); the Session cookie and the `dod` password are never sent there, and only credentials embedded in the URI itself, which the specification allows for a Service Delegate, are used, and only against that host. By default books go to `<data>/<environment>/books/<contentID>/` under the `platformdirs` user data directory; without an Environment, `--output` is required.

The port's `fetch_resource(uri, sink, byte_range)` streams the body to a sink instead of holding it in the Exchange, which keeps only the headers and the first 4 KiB of the body, marked as truncated. A 2xx answer is `Ok` (206 only when a range was asked for) and any other status is a `Deviation`; a resource GET never triggers a relogin (ADR 0005), since only `noActiveSessionFault` does.

Every FAIL and every `Deviation` carries a Spec reference from a closed registry in `domain.v1`, set by the HTTP adapter when it classifies an answer and overridable by a test with a more specific one. A FAIL with no Spec reference is a defect in `dod` and is reported as ERROR. We rejected implicit issuing in `download` (convenient, but it makes the not-issued case untestable), writing resources by `uri` instead of `localURI` (the specification says `uri` may be a script URL), and resume and parallel downloads in v1 (not needed to test a Service).
