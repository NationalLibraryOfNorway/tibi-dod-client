# Known Service deviations are tolerated through opt-in quirks and judged against a baseline

`dod` is a test client that must still be usable against a Service that deviates from DODP v1. Two things are kept apart: reading an answer, and judging it. Tolerant reading (ADR 0004) stays as it is: anything the HTTP adapter can build into a model is `Ok` with its `schema_violations` and Observations, so data commands keep working and Conformance tests turn the violations into FAIL. Only where an answer cannot be read at all, such as an HTTP 500 with no DODP fault element where the specification requires a fault, do we add a **Quirk**: a named, generic workaround inside the HTTP adapter. A Quirk is off by default, is switched on per Environment (`quirks = [...]` in the configuration file, names validated strictly), is never named after a backend but after the behaviour it tolerates, and carries a description and a Spec reference. Using one always produces an `interoperability` Observation, so a deviation is never hidden. Conformance runs ignore Quirks unless `--with-quirks` is given, and the report says so, which keeps a tolerated deviation a FAIL. `dod quirks list` shows every known Quirk with its description and Spec reference and the Environments that enable it; `--env <name>` shows only those enabled for that Environment.

A Quirk may be added by an agent working unattended, but only when all of the following hold: the deviation has been reproduced at least twice against the Service and its Exchange saved masked; it has been checked a second time against the local specification copy and shown not to be a defect in `dod` (namespace, parameter order, soapAction, element order); it has been reproduced as fault injection in the fake Service with a test; it has a Spec reference; and it is off by default. The issue that led to it records which Quirks were added. Deviations that need no Quirk because tolerant reading already copes, such as identifiers that break an XML type, are not Quirks.

Known deviations of a Service are tracked with a **Baseline**: a small file of test ids with a short reason each, containing no addresses or credentials, that belongs to the Service's own repository and not to this one. `dod test run --baseline <file>` compares the run with it. A FAIL that is not in the Baseline is new and gives exit code 1; a baseline entry that now passes is reported as resolved and gives exit code 1 only with `--fail-on-resolved`; ERROR always gives 2, and `--write-baseline <file>` writes a Baseline from the current run. The report gets a `baseline` section with both lists and its schema version is raised. Outcomes themselves do not change: a baselined FAIL is still FAIL in the report, and only the exit code takes the Baseline into account.

We rejected backend profiles (they would tie the tool to particular backends and put their details in a public repository), tolerating everything silently (it would hide the deviations the tool exists to find), a new Outcome for known failures (it would break the four-Outcome model), and keeping Baselines in this repository (they describe a particular Service). Command names that earlier ADRs gave with a `content` prefix are now top-level (`dod download`, `dod issue`, `dod play`); the ADRs have been updated to match.
