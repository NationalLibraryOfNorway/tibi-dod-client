# Masking is always on for files and reports; unmasking is a terminal-only, per-invocation act

Exchanges are unmasked in the port (ADR 0004), so masking happens in one function in the presentation layer that every renderer uses: stderr diagnostics, `--save-exchanges` files and conformance reports. Secrets are the `logOn` password, the values of `Cookie`, `Set-Cookie`, `Authorization` and `Proxy-Authorization`, URL userinfo and credential-like query parameters. A masked value keeps a short hash fingerprint so that two Exchanges can be seen to share a Session.

Two flags lift the masking: `--unmask` for cookies and headers, and a separate `--unmask-password` for the password. Both are command-line only (no environment variable, no configuration setting) and both are refused with exit code 2 unless stderr is a TTY and no file or report output is requested, so unmasked values can never be written to a file, a report, a pipe or the captured output of an agent or CI job. `--unmask-password` additionally needs an interactive confirmation on stdin. Unmasked output is framed by a warning on stderr before and after, and the secrets themselves are highlighted with terminal colour rather than textual markers, so that copying a selected message into another tool still yields valid XML. With `NO_COLOR` set only the warning remains.

This is stricter than the plaintext password in the configuration file (ADR 0006) because transcripts and reports are the artefacts that get pasted into tickets and AI context. We rejected a plain `--unmask` that works everywhere (too easy to leak), no unmasking at all (a proxy is then the only way to see the raw credentials, which is poor for a debugging tool) and textual markers around secrets (they break the syntax of the copied message).
